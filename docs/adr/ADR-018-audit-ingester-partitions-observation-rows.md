# ADR-018: baron's own evidence is not agent activity — the audit ingester partitions it out

| Field | Value |
|---|---|
| **Status** | Accepted (2026-08-09) |
| **Date** | 2026-08-09 |
| **Authors** | Vikram + Claude |
| **Scope** | `skills/multi-agent-audit/` only. No change to `cli/src/baron/` — this is a CONSUMER fix, and the wire shape it consumes is correct as emitted. |
| **Ported from** | `harden/otel` tip `3b9a4d8` (`ingest_otel.partition_guard_records`, `test_no_contamination_from_paired_export`) and ADR-014 §9.1, adapted from that branch's unmerged producer to the merged ADR-013 one |
| **Decision owner** | Vikram |

## 1. The defect

ADR-013 landed an observation plane whose whole design goal was that
`skills/multi-agent-audit/scripts/ingest_otel.py` could read it "with **zero
new code**". That goal was met, and it is exactly the problem.

The rows are *too* compatible. ADR-013 puts `agent.name`, `tool.name` and
`session.id` in the fixed attribute slots of **every** row — correctly: they
are join keys, and `test_baron_attribute_namespace_is_frozen` exists to keep
them un-prefixed for precisely that reason. But those three keys are also the
ingester's `AGENT_KEYS`, `TOOL_NAME_KEYS` and `SESSION_ATTR_KEYS`. So a file
of baron's own governance evidence, handed to the ingester, is read as a
record of agents working.

A guard row is a PreToolUse hook process's evaluation **of** a tool call. It
is not the call, its timestamps are the hook's, and the persona named in it is
the persona guard *adjudicated*, not a persona observed working.

## 2. What actually leaked, measured

On the committed fixtures, with ingester v1.0 and the 11-row
`baron_events.jsonl` (itself generated by a real `baron guard` run — see
`fixtures/gen_baron_events.py`).

**A baron-only export**, every value labelled `measured`:

| metric | v1.0 published | reality |
|---|---|---|
| `session_count` | 1 | no session happened |
| `session_duration_total_s` | 1.096 | the wall-clock of 11 hook subprocesses |
| `distinct_agent_identities` | `["analyst", "pilot", "unknown"]` | two personas guard evaluated, plus a literal default |
| `tool_calls_total` | 11 | guard evaluating 11 calls, plus a `session.start` row |
| `tool_calls_by_name` | `{"Bash": 7, "Write": 3, "session.start": 1}` | `session.start` is not a tool |

**Paired with `flat_spans.jsonl`** — the case that matters, because an auditor
handed both files has no reason to expect one to poison the other. Nine
activity metrics moved:

| metric | alone | paired (v1.0) |
|---|---|---|
| `session_count` | 1 | 2 |
| `session_duration_total_s` | 600.0 | 601.096 |
| `session_duration_p50_s` | **600.0** | **300.548** |
| `tool_calls_total` | 1 | 12 |
| `tool_error_rate` | 1.0 | 0.0833 |
| `tool_calls_by_name` | `{run_sql: 1}` | `+ Bash:7, Write:3, session.start:1` |
| `human_turns_total` | 1, **`measured`** | 1, **`inferred`** |
| `human_turns_per_session_mean` | 1.0, `measured` | 1.0, `inferred` |
| `distinct_agent_identities` | `["researcher"]` | `+ analyst, pilot, unknown` |

The same pairing moves 10 metrics on `otlp_two_sessions.json` and 6 on
`missing_attrs.jsonl`.

Two of these deserve naming. `session_duration_p50_s` **halving** is
instrumentation overhead published as agent working time under a `measured`
label — the 0.53 failure mode with the sign flipped, and worse than an
over-claim about capabilities because nothing in the output hints at it.
`human_turns_total` **silently downgrading** from `measured` to `inferred` is
the honesty ladder being walked *backwards* by the arrival of evidence: the
fabricated session has no logs stream, so the ingester correctly reports
partial coverage of a session that does not exist.

`harden/otel` measured the same class of defect against its own producer
(`session_duration_p50_s` 600.0 → 300.297, roster polluted with two personas)
and recorded it in ADR-014 §9.1. This branch's numbers are worse only because
ADR-013 additionally puts `tool.name` on every row.

**How the figures above are held to account.** Every figure in the two tables
is pinned as a literal in `tests/test_ingest_otel.py`
(`ADR018_BARON_ONLY`, `ADR018_FLAT_PAIRED`) and recomputed from the committed
fixture on every run by `test_adr018_published_figures_reproduce`, which
emulates ingester v1.0 in-process. That closes *literal ⇄ fixture*.
`test_adr018_tables_quote_the_pinned_figures` then reads this file back off
disk and checks that each metric's row in those two tables mentions every part
of its pinned value, closing *ADR ⇄ literal*. It is deliberately a
token-presence check over the whole row rather than a parse of one cell,
because the "paired" column is written as a delta (`+ Bash:7, …`) and the
unchanged parts live in the neighbouring cell; small integers therefore match
loosely. Not mechanised, and manual: the confidence labels, the moved-metric
counts in the sentence above (`ADR018_MOVED_COUNTS` pins and recomputes them,
but no test reads them back out of this prose), and every number in §4. The
earlier claim here — that the test "fails if the ADR and the committed fixture
disagree" — was false of the ADR half: editing `300.548` to `999.999` in the
table left the suite green. It fails now.

The figures are tied to the *committed* `baron_events.jsonl`:
`gen_baron_events.py` shells out
to a real `baron guard` run, so re-running it produces different hook
wall-clocks and these durations move. That is what happened to the first draft
of this ADR, which published durations from a generation run that was then
replaced by the fixture actually committed — the numbers were real but no
longer reproducible, which in a repo that publishes its own fidelity as 0.53
is the same defect as an invented one. Hence the test.

## 3. Decision

`ingest_otel.compute_metrics` calls `partition_guard_records(records)` **before
`build_sessions`**. Everything downstream sees agent activity only; the
withheld rows are counted on their own axis and appended last.

**The partition predicate is the `baron.outcome` attribute**, not a span-name
allowlist. ADR-013 guarantees that slot on every row and explicitly refuses to
close the `kind` vocabulary, so keying on the attribute means a kind added to
the registry tomorrow partitions correctly with no change here. Known span
names are matched too, as a belt-and-braces convenience, including ADR-014's
`baron.guard.evaluate` so an export from that (unmerged, possibly
third-party) producer is handled as well.

**All six ADR-013 kinds are partitioned, not just the guard ones**, even
though the function keeps the ported name `partition_guard_records`. The
evidence kinds arrive through the same file and carry the same three
contaminating keys; `tool.post` in particular carries `tool.name` and would be
counted as a tool call. See §5 for why `tool.post` is not folded into
`tool_calls_total` instead.

**Two new aggregate keys**, both `measured`, both direct counts:

- `guard_decisions` — `baron.outcome` over the adjudication kinds only
  (`guard.decision`, `guard.override`). Canonical values are zero-filled so a
  dashboard column never silently disappears; unrecognised values are counted
  under their own key rather than dropped.
- `baron_events_by_kind` — every partitioned row by span name. This exists so
  the exclusion is **auditable rather than silent**: a reader can see that 11
  rows were withheld and what they were. Partitioning evidence out and
  publishing nothing would be its own quiet dishonesty.

**Absence notes tell the truth.** A baron-only export previously reported "no
parseable records", which is false — the records parsed fine, they are not
activity. `absent_activity()` supplies a note that says so and points at the
axis where the rows *are* counted. With no baron rows present it returns the
byte-identical pre-v1.1 note, which is what makes the change additive.

`any_spans` is now computed over the activity records rather than the
per-file span counts, so a baron-only file is not mistaken for a spans stream
— which would publish a `measured` zero tool calls for an export that never
described any.

`INGESTER_VERSION` → `1.1`. `merge_telemetry.TELEMETRY_KEYS` gains both keys
(it is an allowlist, not a passthrough).

## 4. Evidence that the fix is load-bearing

`test_no_contamination_from_paired_export` pairs each pre-v1.1 fixture with
the baron export and demands every activity metric, every confidence label,
every note and the whole per-session breakdown hold still — with `source` the
single permitted delta, pinned to exactly "gained the baron filename".

**Verified by reverting the fix**, because a test that cannot fail is not
evidence. Two different mutations were run, and they are *not*
interchangeable — the difference is the correction this revision exists to
make:

| mutation | what it removes | result |
|---|---|---|
| `return records, baron` | the partition and only the partition — baron rows go back into the activity plane, the guard-decision axis still sees them | the suite **completes**: **45 failed checks** |
| `return records, []` | the partition *and* the guard-decision axis — i.e. the v1.0 shape, which had no such axis | dies in `test_baron_guard_metrics` with an `AttributeError` after 17 failed checks, because `guard_decisions` degrades to the string `not measurable` and the test sums it |

The first is the precise inverse of this change and is the figure to quote:
**45 failed checks**. The 45 is stable across every commit on this branch,
while the denominator moves as checks are added — 45 of 230 at `4a85a49`, 45
of 247 at `30a1002`, 45 of 263 at this revision. All three were run.

**Retraction.** An earlier revision of this section said "there is no honest
'N of M failed' figure for the suite under revert" and called round 1's 45 an
artefact of a run that no longer reproduced. Both statements were wrong. 45
reproduces, and the `AttributeError` used to justify the retraction belongs to
the *second* mutation, which additionally empties the guard-decision axis §3
introduces — a different defect from leaving baron rows in the activity plane.
Corrected here rather than quietly deleted: a wrong retraction is worse than
the claim it retracted, because it reads as diligence.

Run on its own rather than as part of the suite, the contamination test fails
**34 checks** under *either* mutation (10 on `flat_spans.jsonl`, 11 on
`otlp_two_sessions.json`, 7 on `missing_attrs.jsonl`, 6 named checks — each
fixture contributing its moved metrics plus one per-session-breakdown check).
The two agree there because the guard axis is not on that test's comparison
surface. With the fix in place the whole suite completes: **263 pass, 0 fail**.

The test helper that stubs the partition, `_unpartitioned`, uses the *second*
form, correctly: it exists to reproduce what ingester v1.0 published, and v1.0
had no guard axis. Its docstring now says so explicitly, because reusing it as
the mental model of "the revert" is what produced the error above.

§2's figures are themselves under test —
`test_adr018_published_figures_reproduce` recomputes every number in those two
tables from the committed fixture with the partition stubbed out, and
`test_adr018_tables_quote_the_pinned_figures` checks the tables here still
quote them (§2 states the exact scope of both). `gen_baron_events.py` shells
out to a real `baron guard`, so its hook wall-clocks are not stable across
runs; without those tests, regenerating the fixture silently falsifies this
ADR instead of failing a build. That is exactly how the first draft's
durations went stale.

The companion `test_additivity_lock` is the weaker half and says so in its own
docstring: it only ever reads guard-free fixtures, so it can never catch
contamination. `harden/otel`'s round 2 cited that lock as proof of a change it
could not possibly have tested. Its baseline,
`golden_pre_baron_metrics.json`, is generated by
`gen_golden_pre_baron_metrics.py`, which extracts `ingest_otel.py` from a git
ref and refuses to run unless that copy reports `INGESTER_VERSION == "1.0"` —
without that check a regenerated golden would approve its own drift.

The skill's test file was never wired into CI. It is now
(`.github/workflows/ci.yml`, stdlib-only step alongside the other two), so the
next divergence between baron's emitted shape and the ingester that reads it
fails a build instead of a report.

## 5. What this ADR deliberately does NOT do

**No aggregate over `baron.enforcement`.** `harden/otel` shipped a
`guard_enforcement_class` metric and it is not ported. That attribute is under
correction: baron derives it from the rules artifact's static `detection`
field, and DECISIONS-FOR-REVIEW D1 / ADR-013 §9.1 measured it wrong in both
directions — a structural refusal (a write escaping the repo root, where every
persona is denied identically and no capability adjudicated anything) is
booked `enforced`; a genuine persona-dependent allow is booked
`not-applicable`. Both mislabelled rows are in the committed fixture, and
`test_baron_guard_metrics` asserts the over-count case so the day the producer
is corrected, the test is the thing that says why.

Publishing a `measured` aggregate over a field whose producer-side definition
is known wrong is the exact over-claim ADR-002 and ADR-008 forbid, and it is
worse than not shipping the metric: the count would look authoritative. The
axis lands when the label does — see the owner's D1 decision (`enforced` /
`unevaluated` / `unknown`, derived from an explicit `Decision.adjudicated`
flag).

**No fold of `tool.post` into `tool_calls_total`.** A PostToolUse row is a
real record that a tool call completed, and folding it in is tempting. It is
refused because it would mix two populations under one `measured` label: the
row only exists where the PostToolUse hook is wired, so the total would be a
silent undercount whose size depends on deployment, not on behaviour. That is
the same failure the badminton-analyzer incident (ADR-017 §1) is about.

**No per-session guard breakdown.** It would change the shape of every session
object and break the additivity contract for zero measured need.

**No change to `cli/src/baron/`.** The wire shape is right; the consumer was
wrong. Fixing this by stripping join keys from baron's rows would break the
correlation those keys exist to enable.

## 6. Consequences

- An auditor can hand over a `.baron/events/*.jsonl` file alongside a Claude
  Code export and the two planes stay separate, correlated only by the
  `session.id` both carry.
- A baron-only export reports every activity metric `not measurable` with a
  note explaining why. That is a *less* impressive report than v1.0 produced,
  and it is the correct one.
- **Cross-version hazard.** A pre-v1.1 ingester pointed at a baron export
  still produces every number in §2. Snapshots carry
  `telemetry_metrics_version`; check it before trusting one that mixed
  sources. This cannot be fixed from baron's side without removing the join
  keys.
- `guard_decisions` is evidence that guard is live and blocking. It is **not**
  an operational-fidelity numerator — it measures the traffic mix of one
  export. The metric carries that warning in its own `note`, not only here.
